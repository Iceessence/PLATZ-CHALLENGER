**Purpose.** This document is the complete product and engineering constitution for a **new, independent implementation** of PLATZ. **The permanent operating principle:**

> Improve the actual PLATZ application in the way that delivers the greatest verified long-term value. Preserve correct functionality, build several meaningful capabilities when feasible, update every affected user interface and integration, use current suitable technology with efficient investigation, and prefer complete, durable product quality over impressive demonstrations or activity counts.

A built executable does not prove all features; a screenshot does not prove a renderer; a README does not prove behavior; a successful shader compiler probe does not prove a complete Studio.

# PART I — ONE PRODUCT, ONE COMPLETE USER EXPERIENCE

## 1. The true PLATZ goal

PLATZ is a unified local-first creative workstation with a genuine high-end 3D/2D game engine, a deeply integrated professional creation Studio, advanced authoring tools, no-code and expert coding, and increasingly original locally developed PLATZ AI. Its logical components are **PLATZ Hub, PLATZ Studio, PLATZ Core, PLATZ Engine, PLATZ Runtime, and PLATZ AI**. These are components of **one product**, not different apps that require manual file exchange.

The long-term vision includes the useful sophistication of major game engines, 3D modeling and sculpting suites, material editors, pixel-art and illustration tools, animation and audio/video software, code IDEs, documents/data workspaces, and specialized AI systems. These are capability benchmarks, not permission to copy third-party source or imply instant feature parity. Users should work in one source-connected project: create an editable asset, view it in the actual engine, control its behavior visually or with code, press Play, save, recover and export it without destructive round trips.

A coherent beginner workflow must coexist with professional precision, extensibility and deep control. A powerful advanced feature that cannot be found, operated, saved or explained through its UI is not finished. Professional UI/UX is implemented **alongside** every new feature, not postponed to a future polish phase.

## 2. The five defining product promises

1. **Live source-connected creation:** visual art, mesh data, materials, rules, code, animation, and runtime are derived from durable editable authoring state, with appropriate incremental updates rather than manual reimport loops.
2. **Engine and editor are real from the outset:** the Vulkan-rendered viewport operates on the actual project scene. Scene picking, editing, save/reopen and Play use genuine connected systems. There is no decorative isometric surrogate or screenshot-based editor.
3. **No-code depth and code freedom:** non-programmers can build complex experiences through understandable behavior tools while engineers can code, debug, automate and extend; both approaches agree on shared semantics when equivalence is promised.
4. **Original PLATZ AI as a product goal:** PLATZ progressively develops its own trained specialist models, qualified procedures, memory/knowledge organization and safe project operations; third-party pretrained models may be optional tools or teachers, never falsely represented as original PLATZ intelligence.
5. **Project and owner sovereignty:** source data, user projects and personal information remain under the owner's control, with recoverable changes, scoped automation, offline functionality, clear provenance, and no unauthorized money, identity, accounts or private-data use.

## 3. Product organization and interaction

PLATZ Hub discovers projects, creation tasks and user workspaces. Studio provides context-sensitive, user-customizable professional tools. Core owns canonical project state, assets, IDs, revisions, commands and permissions. Engine provides rendering, simulation and editor/runtime support. Runtime executes games and interactive experiences without requiring editor-only services. PLATZ AI uses authorized project commands and qualified models.

Default task areas may include World, Model, Art, Materials, Animate, Logic, Build and AI/Development, but the UI must not become a cockpit of hundreds of unrelated buttons. Use useful defaults, progressive complexity, search/command discovery, keyboard access, accessible controls, numerical precision, workspace layouts and UI customization. The final goal includes visual editing of PLATZ's own UI, while approval/Stop/security controls remain protected.

## 4. Creation scope by domain

**Engine and worlds:** true 3D and pixel-exact 2D, PBR materials, modern lighting, ray tracing, shadows, terrain, streaming, voxels, physics, navigation, actors, vehicles, multiplayer, saved gameplay, procedural systems and advanced simulations. No unconditional FPS or rendering-fidelity guarantees.

**3D creation:** mesh modeling, non-destructive modifiers, sculpting, UVs, retopology, baking, rigging, skinning, animation, material painting, procedural geometry, character/creature production and interchangeable asset formats.

**2D and visual arts:** layered raster painting, stylus support, vector paths, professional brushes, comics/manga layout, pixel-perfect sprites, tilemaps, palettes, animation, typography, color management, digital and print export.

**Media and technical tools:** animation timelines, cinematic sequencing, VFX, audio, video, code IDE/workflows, documents, data, visualization and other compatible professional creation domains as later qualified releases.

**Creation logic:** reusable game components, events/conditions/actions, state machines, graphs, dialogue, quests, HUD, inspector-bound variables, data tables, validation and visual debugging.

**Intelligence:** safe project-aware assistant operations, original compact models and specialists, verifiable knowledge and procedures, structured creative output, model-training/evaluation workbench, multi-agent coordination and independently validated autonomous improvement.

All these capabilities remain in the 401 detailed long-term contracts in Part VI. Prioritize integrated engine and creator workflows first; do not abandon the broader vision.

# PART II — FAIR, INDEPENDENT TWO-AI DEVELOPMENT

## 5. Two implementations of the *same* PLATZ

The original AI's project exists at `C:\PLATZ`. **Never edit, rename, delete, inspect or import from that repository**, including its Git history, binaries, archives, screenshots, generated data or dependency caches, without explicit later permission. The new AI develops the same product independently at:

**`C:\PLATZ-CHALLENGER`**

If the folder already exists, inspect it and avoid overwriting unrelated work; request authorization only if a safe isolated directory cannot be established. Once initialized, it becomes the permanent canonical repository for the challenger. The resulting app may still be named **PLATZ.exe** because the folders isolate it. Do not install global tools, create machine-wide file associations, write into Program Files, or modify environment configuration in a way that affects the other implementation without express authorization.

Both implementations should be assessed under the *same specification, feature-order gates, hardware where practical, and acceptance tests*. The challenger must **not** attempt to imitate or reverse engineer the existing developer's source. Architectural differences are allowed only within the explicit binding constraints below and must be documented. When testing the two apps, avoid concurrent runs if shared GPU/CPU use would distort performance.

### A fair comparison requires known experimental conditions

- Freeze the document/version identifiers, starting source revision, declared budget (wall-clock and/or AI usage when available), benchmark scenes, resolution, graphics options, driver and machine state.
- Evaluate equivalent feature scope and elapsed/usage budget. Comparing a mature original against a greenfield challenger without normalizing for progress or development effort is an *informal product comparison*, not an equal-start experiment.
- Run the same workflow and negative tests. Record passes, failures and not-run cases; no scoring from unsupported claims.
- Do not cross-pollinate source, code patches or solutions while the head-to-head is active. The owner may later authorize a separately reviewed merge of verified ideas.
- Keep independent Git commits and build artifacts. Neither author independently approves its own work.

## 6. Shared first-delivery feature gates

**Gate 0 — Reproducible, safe engineering foundation.** Clean isolated Git repository, full source tree and dependency manifest, appropriate toolchains, documented build commands, truthful capabilities, correct resource ownership and basic tests. The output must not be merely a framework probe or source-less binary.

**Gate 1 — Genuine engine/editor/runtime vertical slice.** Launch the real PLATZ Studio; load an editable PLATZ project; render actual 3D meshes with Vulkan, perspective, depth and transforms; navigate camera; pick/select and edit an object; create/duplicate/delete where supported; undo/redo; save/reopen with IDs intact; enter Play, interact and exit without modifying authoring state; inspect and validate real UI; record build/run evidence and executable path. This is **the actual product**, not a detachable demo.

**Gate 2 — Professional creation expansion.** Complete the next coherent batch of: mesh import with preserved source and asset references; usable viewport move/rotate/scale and numeric Inspector; editing selection/snapping; editable material and texture pipeline; appropriate lighting and PBR; improved user-facing workflows. Every chosen feature must update UI, persistence, undo, rendering, asset references and tests where applicable.

**Gate 3 — Gameplay and original AI foundations.** Improve meaningful gameplay and visual behavior (not just rotating a cube). Expose reversible typed project commands with revision and permission checks, establishing the protected path for genuine project-aware AI and eventual original specialist-model training. Do not claim original models until training and evaluation have occurred.

**Gate 4 and onward — Deep creator capabilities.** Expand into sophisticated 2D/3D art, no-code, animation, graphics quality, world tooling, runtime packaging, original AI model development and other domains in the capability register. The ordering within an active gate can be adapted to measured dependencies, but feature completeness and regressions remain mandatory.

A failure to finish a gate within a usage-limited session is not permission to misreport it. Preserve working intermediate code, exact incomplete checks, and a high-quality handoff so progress continues on the next activation.

# PART III — REQUIRED ENGINEERING BASELINE

## 7. Technology selection: newest *suitable* stable, reproducible and secure

The challenger must use a coherent, modern native architecture matching the product requirements, not choose older installed tools simply to save setup time. Use the **most recent supported stable general-availability version suitable for this system at the moment of initialization**, verify the real release, then **pin exact versions** in dependency manifests and an architecture record. Reassess only for known security defects, compatibility barriers or meaningful measured benefit. Do not constantly chase nightlies, prerelease toolchains or an imaginary version number.

**Binding baseline for a matched comparison** (record exceptions with specific reproducible evidence and owner authorization):

- **Primary language:** Native C++23 when supported; C++20 if a documented compiler/dependency incompatibility warrants it — Real engine, Core and Runtime; clean module boundaries and lifetime ownership
- **Primary graphics API:** **Vulkan 1.4** — Real device, feature negotiation, synchronization, GPU resource control, graphics and compute; no default D3D12 or simulated rendering
- **Vulkan SDK:** Current stable LunarG/Khronos compatible Vulkan 1.4 SDK — Verify installation and driver support; do not assume newest headers imply GPU features
- **Memory allocation:** **Vulkan Memory Allocator (VMA)** — Use a tested stable release; PLATZ owns higher-level residency, pools, lifetime and budgets
- **Shaders:** **Slang-authored PLATZ shaders compiled to SPIR-V** — Validate compiler, SPIR-V, reflection, error reporting and hot reload; HLSL/DXC permitted as qualified fallback
- **Platform:** **SDL3** — Window creation, input, Vulkan surfaces, DPI and lifecycle; do not let UI framework own engine rendering
- **Editor UI:** **PLATZ-owned component/layout/binding architecture** using qualified mature supporting libraries — Integrated professional UI with docking, text, focus, keyboard, DPI and accessibility; no detached debug UI as permanent Studio
- **Project metadata:** **SQLite** — Appropriate transactions, revisions, IDs and schema migrations—not the sole store for all heavy binary assets
- **Large assets:** **PLATZ-owned content-addressed asset storage** — Integrity, dependency references, staging, recoverable commits, garbage collection and preservation of editable source
- **Build/test:** **CMake, CTest, Git, current stable compiler, dependency lock, reproducible presets** — Clean x64 Debug/Release builds and documented launch path
- **Graphics diagnostics:** Khronos validation layers, synchronization validation, RenderDoc / GPU profilers as available — Evidence-backed GPU correctness, resource lifecycle and performance

**Version candidates verified November 21, 2026 (not eternal pins):** Vulkan SDK 1.4.363 series, SDL3 3.4.20, VMA 3.5.0, Slang 2026.22.1 series, CMake 4.5, SQLite 3.54.1. Independently check official stable versions and compatibility before locking; if a release is unavailable or has a known defect, choose the newest suitable stable alternative and record why. Current official references: https://vulkan.lunarg.com/ , https://github.com/libsdl-org/SDL/releases , https://github.com/GPUOpen-LibrariesAndSDKs/VulkanMemoryAllocator , https://github.com/shader-slang/slang/releases , https://cmake.org/download/ , https://sqlite.org/releaselog/current.html .

**Library policy:** PLATZ owns its architecture, renderer, materials, scene semantics, editing commands and UI system. It does **not** need to recreate Vulkan memory allocators, cross-platform windowing, shader compilers, text shaping, codecs or databases merely for originality. Verify licenses, pin sources, hash downloaded dependencies where practicable, and avoid automatic user-account registration, paid services, or arbitrary scripts.

## 8. Vulkan-first renderer: minimum production-grade responsibilities

PLATZ owns Vulkan instance/device/queue negotiation, capability profiles, presentation, GPU resources, frame scheduling, shaders/pipelines, descriptors, graphics/compute queues, frame pacing, resource labels and diagnostics. Maintain a credible path toward advanced PBR, compute, shadow systems, geometry streaming, ray tracing and path tracing. No full engine wrapper or tutorial graphics copied and claimed as PLATZ without source ownership and licensing compliance.

**GPU memory:** Use VMA as the allocation/suballocation layer. Above it, implement typed RAII resource wrappers, generation-aware handles where useful, upload/readback rings, transient pools, explicit residency and eviction policies, budget accounting, deferred destruction, coherent/noncoherent mapping rules and out-of-memory recovery. VMA does not automatically govern allocations in external CUDA/AI processes.

**Shader pipeline:** PLATZ writes its shader logic in Slang where qualified; Slang (or DXC fallback) compiles to SPIR-V. Implement compilation diagnostics, SPIR-V validation, reflection-driven binding checks, parameter-layout stability, cache invalidation, module/variant tracking and safe hot reload with last-good state. Do **not** create a shader compiler in the first production stage. Keep material source graphs and parameters editable.

**Synchronization & frame scheduling:** Use correct Synchronization2 and appropriate timeline/binary semaphores, fences, layout transitions, resource and descriptor lifetime protection, frames in flight and queue ownership. Do not conceal hazards with per-frame `vkDeviceWaitIdle` or global barriers. Develop Vulkan validation/synchronization checks early.

**Pipeline architecture:** Prefer appropriate dynamic rendering and clear pass dependencies, then evolve toward a measured render graph managing temporary resources, barriers, aliasing and pass scheduling. Shader/pipeline caches must incorporate driver/device/compiler and shader inputs when needed. Avoid disruptive shader compilation in the main render loop.

**Presentation and recovery:** Handle resize, minimization, DPI, swapchain recreation, surface loss, presentation mode changes, feature absence and plausible device loss. Profile actual GPU timestamps/frame times and memory; do not claim universal hardware features or FPS. A non-RTX tier may need reduced rendering options without losing project integrity.

**Precision and color:** Keep pixel-exact 2D/color workflows independent where necessary from HDR/3D tone mapping and temporal AA. Plan for appropriate large-world precision and professional color-management paths; do not implement premature advanced renderer features in place of basic studio completeness.

## 9. PLATZ-owned UI without a years-long UI framework detour

A native interface is a **product system**, not the demand to reinvent text shaping, layout, font rasterization, accessibility APIs, drag/drop, clipboards, IME or screen readers. Choose a bounded foundation (for example, SDL3 plus a qualified layout/text/UI library) and build PLATZ-owned typed widgets, theme rules, workspace layout, docking behavior, property bindings and safe customization on it. Do not adopt Qt simply because another implementation did; do not reject all mature toolkits without evidence either. If a candidate has unacceptable accessibility/IME/docking limitations, make one focused decision and move on.

The first usable Studio must visibly support: clean scene viewport, hierarchy, Inspector, project/asset access, Play/Stop, selection and numeric transform editing; readable scalable typography, keyboard focus, copy/paste, high-DPI, layout persistence and working errors. As node editors, timelines, material graphs and AI sessions appear, their interactions and UX must become part of the same coherent visual system. Protect user approval and Stop controls from unsafe customization. Screenshot beauty alone is insufficient: interactions are tested.

## 10. Canonical editable project system

Define durable ObjectIdentity, typed components/relationships, asset identity, immutable or reliably versioned source assets, revision heads, undo/redo records, staging, migration and path provenance. Persist structured metadata and transactional revisions in SQLite as appropriate. Place large assets in a managed content-addressed store; ensure staged asset writes are durable before advancing canonical revision heads, recover safely from partial commits and do not delete live blobs. Validate hashes, links and schema.

The authoring scene and Play-state projection must use the same semantic data but remain safely isolated, so a stopped Play session does not unexpectedly persist runtime edits. GPU uploads and cache structures are derived from canonical authoring source, not the sole copy. Implement repeatable creation/save/reopen, restart-crash recovery, stale revision rejection and asset corruption checks. Expose a versioned typed command registry with expected revision, permissions and reversible effects for future no-code/code/AI use.

## 11. PLATZ AI: own the intelligence goal and protect user authority

Develop original small specialist models, local factual/procedural knowledge, qualified coordinated roles, model training and evaluation, and project-aware editing over time. Do not conflate an API call or downloaded pretrained model with original trained intelligence. Establish typed project commands, safe staging, revision pinning, edit diff, confirmation and rollback early; then integrate useful project queries and actions. Separate automatic implementation and review authority; an author may not independently approve its own changes.

AI model inference, rendering, GPU compute and background training compete for GPU/VRAM. Implement an evidence-based scheduler with authoring priority, bounded generation and owner-authorized idle training; degrade safely rather than crashing. No autonomous purchase or account creation, no use of the owner's payments, identity, subscriptions or private data, and no untrusted host execution outside qualified isolation. Native PLATZ model training must be reported only when it actually runs with repeatable evaluations.

## 12. Safety and adversarial qualification

The implementation must fail safely under input corruption, stale object/revision writes, save interruption, external asset loss, path traversal/symlinks/reparse aliases, resource exhaustion, plugin/script escape attempts, AI Stop followed by late commit, duplicate state in games, and conflicting edits. Only activate domain-specific tests when corresponding features exist, but do not omit the relevant current security tests. No personal-account, money, identity, private-data or unauthorized network use. Document dependencies' licenses and restrict unknown executable downloads.

**`AGENTS.md` / handoff contract:** every new session reads the approved Master and current canonical handoff, then inspects actual source/commits. The handoff contains tested facts, exact version pins, the active release gate, features completed and not completed, build commands, current blocker, next integrated task and known security/quality risks. It must be updated before usage ends. Never re-plan the entire vision in each session.

## 14. Complete-feature contract

The developer must deliver more than source files. For each activated feature, identify currently existing affected surfaces and implement them together:

- Real functional behavior and error handling.
- Usable, professional UI/UX and accessibility relevant to that feature.
- Canonical project representation, save/reopen, revisions and undo/redo where applicable.
- Rendering, asset pipeline and actual runtime behavior where applicable.
- No-code, coding and PLATZ AI command surfaces *when those capabilities exist*.
- Performance/memory and security implications.
- Automated tests, interactive acceptance and validation-project coverage.
- Help/discoverability and honest release status.

If an interface does not exist yet, record its future integration requirement explicitly, without wasting time on decorative stubs. Never call a feature complete when a currently applicable integration remains broken.

## 15. Usage efficiency, progress and loop prevention

Read the full product specification once at first activation; thereafter use the short handoff, relevant requirements and repository reality. Inspect tools/versions once, pin them, and stop chasing newer releases absent a concrete security/compatibility issue. Do not use an elaborate architecture research report as a substitute for product code. Prefer several substantial, coherent outcomes in a session over dozens of cosmetic changes or undocumented placeholders.

If two substantially similar attempts fail, stop repeating the patch: isolate a minimal reproducible failing test, challenge the assumption, change approach and preserve diagnostic evidence. If a major blocker remains, deliver a useful independent integrated task without hiding the blocker. Maintain approximately five meaningful progress updates in a large session when practical; report actual work, not endless status narration. Respect usage exhaustion by ensuring every finished batch leaves committed, recoverable work and a handoff.

## 16. Build, test, launch and score

Mandatory for a claim of Gate 1 verification: reproducible clean Windows x64 Release build, real app startup, genuine Vulkan device/graphics execution, visible 3D scene, project object changes bound to Inspector and renderer, Play/Stop, save/reopen, current relevant regression tests and a path to an actual `PLATZ.exe`. If physical GUI testing is unavailable, accurately mark GUI checks not run—do not claim them passed.

For later gates, exercise professional user workflows using a shared **feature-acceptance script**, not screenshots alone. Collect CPU/GPU frame time, RAM/VRAM, cold launch, scene open/save time, crash/validation errors, tests, application responsiveness and appropriate user-task completion. Record GPU/driver/resolution/settings and test scene identity; compare only under matched conditions. Never invent benchmark numbers.

### Independent comparison rubric (100 points; evidence only)

- **25 points — End-to-end working creator capabilities:** Completed Gates, depth, save/reopen, integrated user journeys
- **20 points — Professional UI and UX:** Real interactions, keyboard/focus, polish, discoverability, responsive editing
- **15 points — Vulkan renderer and future scalability:** Correct GPU execution, resource lifetimes, shader pipeline, diagnostics, rendering quality
- **15 points — Data integrity, regressions and security:** Executed tests, crash recovery, revisions, negative tests, no silent corruption
- **10 points — PLATZ AI foundation/original intelligence progress:** Authorized project operations; trained native model proof where claimed

**Hard gates override scores:** an application that cannot launch, corrupts project data, fakes 3D rendering or evades authorization cannot be declared the winning implementation on appearance or feature count. Mark `NOT RUN` separately from `FAIL`. Do not turn differing AI usage limits into an invented equal-cost claim. Preserve independent review and owner decision authority.

The **401 independently addressable targets below** describe the full ambition and its testable behavioral intent.
